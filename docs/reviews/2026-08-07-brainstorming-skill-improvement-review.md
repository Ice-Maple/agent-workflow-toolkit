# 评审：Brainstorming Skill 方案比较机制改造方案

- 日期：2026-08-07
- 评审对象：`docs/plans/2026-08-07-brainstorming-skill-improvement.md`
- 对照材料：`skills/brainstorming/SKILL.md`、`references/sessions/019fcfb1-5dff-7e43-8b99-d2beefc8901a-questions-and-choices.md`、`references/superpowers/brainstorming/SKILL.md`、`AGENTS.md`
- 评审方式：缺陷优先，只记录会影响正确性、可实施性、可验证性或问题界定可信度的问题

## Findings

### [P1] 修改范围仍锚定“提出 2–3 个方案”，无法覆盖会话中真实失效的全程选择题路径 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:206-213`

问题界定依据的是整段会话里约 27 个带候选方案的问题，而不是单次“核心方案比较”。但第 6.2 节只把现有流程第 3 步拆成比较 / 推荐 / 选定后设计；第 2 步“逐个澄清问题”未规定决策归属、可行性门槛和等深度比较是否适用。

按当前写法，实施者可以只改“提出方案”一节，澄清阶段仍继续产出“A 详细展开 + B/C 陪跑 + 是否确认 A”。这与第 2.2 节诊断的失效模式不一致，也与第 4.1 节“只有用户拥有的重大取舍才做 A/B/C”未形成可落地的流程挂钩。

**建议：** 明确写清：凡向用户展示候选方向的问题，都先做决策归属判断；等深度四字段主要用于真实替代方案比较；澄清类问题若仍给选项，至少不得出现推荐项单边详细设计和“是否确认 A”默认动作。第 6.2 节应同时改写流程第 2、3 步，而不是只拆第 3 步。

### [P1] 静态验证依赖仓库内不存在的 `quick_validate.py`，步骤不可复现 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:291`

第 9.1 节要求“Skill 名称和目录结构通过 `quick_validate.py`”，但本仓库无该脚本；当前环境中对应实现位于 Codex 系统 Skill 路径 `~/.codex/skills/.system/skill-creator/scripts/quick_validate.py`。计划未给出调用命令、工作目录或是否把校验脚本纳入仓库。

按字面执行，实施者无法在本仓库完成该验收项，或会误以为仓库已具备该工具。

**建议：** 写明绝对/相对调用路径与示例命令；或把最小校验收入仓库；或改为可在本仓库执行的等价检查（frontmatter 字段、`name`/`description`、目录结构、行数、`git diff --check`）。

### [P2] 完成定义把单机安装副本同步写成仓库级完成条件 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:331-337`

第 11 节把“已安装副本与仓库源文件一致”列为改造完成条件，安装路径还指向本机 `C:\Users\shterm\.codex\skills\brainstorming\SKILL.md`。这对作者本机生效有用，但不适合作通用仓库能力的完成定义：他人克隆仓库、CI、或未使用该 Codex skills 目录的环境无法满足。

**建议：** 将仓库完成条件收敛为：源文件已改、静态校验通过、行为验证证据齐全、Skill 保持轻量且无 Superpowers 依赖。安装副本同步与哈希核对保留为“本机生效检查 / 发布步骤”，不要写入仓库级 DoD。

### [P2] 证据陈述过度简化用户选择，削弱问题界定可信度 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:38-42`

计划写“用户仅在 Q27 选择了 B，其余选择基本沿着 A 推进”。对照会话记录：

- Q13 用户明确拒绝 A，要求 BC 结合；
- 多处回答是“A，但……”并追加实质性约束或改写；
- Q26 是落盘确认，不是候选方案比较；Q28 仍是带推荐的 A/B/C。

“A 被详细展开、B/C 陪跑、问法变成确认 A”这一诊断仍然成立，但“仅 Q27 偏离 A”不准确。过强表述会让后续读者怀疑整段证据。

**建议：** 改成可核验表述，例如：绝大多数问题将 A 标为推荐并只详细展开 A；用户多数接受 A 或在 A 上修补；明确拒绝推荐并改选其他方向的情况至少包括 Q13、Q27。

### [P2] 行为验证有场景无证据协议，验收不可判定 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:297-316`

六类行为场景方向正确，但缺少：

- 每类场景的原始输入 fixture 或最小提示词；
- 观察点与通过/失败判定表；
- 会话记录或摘录落盘位置；
- “不再稳定出现……”的判定窗口（一次通过、连续 N 次、或多模型抽检）。

结合 `AGENTS.md` 对能力需要明确 evidence 与相称验证策略的要求，当前第 9.2/9.3 节还停留在愿望清单，实施后容易变成口头宣称通过。

**建议：** 为 6 个场景各补一行：输入摘要、期望可见行为、禁止行为、证据保存路径。完成定义改为“六类场景均有可复查记录且满足验收表”，而不是抽象的“覆盖上述六类场景”。

### [P3] 澄清题与方案比较题共用同一深度标准，边界未定义 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:112-129`

第 4.3 节要求选择前统一四字段比较。若澄清阶段的偏好/范围问题也强制四字段，消息会迅速变长，可能用新的阅读负担替换旧的确认疲劳；若澄清题完全豁免，又容易退回陪跑项模式。

**建议：** 区分两档：

1. 真实替代方案比较：四字段等深度；
2. 目标/偏好澄清：可更短，但每个选项仍需一句真实适用条件，且禁止推荐项单边详设和“是否确认 A”。

### [P3] “保持紧凑”与新增规则块缺少裁剪策略 — `docs/plans/2026-08-07-brainstorming-skill-improvement.md:279-280`

计划新增原则、决策归属、可行性门槛、四字段比较、推荐分离、发送前检查、常见误区和落盘模板，同时要求核心指令紧凑、行数明显低于 500。当前 `SKILL.md` 仅约 121 行；计划未说明若正文膨胀时优先保留什么、删除什么，也未给出目标行数或“只改 SKILL.md、不新增参考文档”的冲突处理。

**建议：** 增加体量预算，例如目标 ≤200–250 行；发送前检查保持 5–7 条短清单；反例用一行一条；避免把第 4 章设计说明原样搬进 Skill。

## 总体评估

方向正确，且与证据匹配：保留方案比较，但拆开“等深度比较 / 条件式推荐 / 选定后再详设”，并拒绝把 Superpowers 硬门禁和后续 Skill 链带回来。第 4.1–4.6 节的机制设计足以解释并抑制参考会话中的偏置模式。

当前主要风险不是思路错误，而是**实施映射偏窄**和**验收不可执行**：若不先修正“全程选择题都要过决策归属”、校验命令可复现、行为证据可落盘这三项，按该方案改完的 Skill 仍可能在澄清阶段复现旧交互，并通过无法复查的“行为验证”被标为完成。

## 建议的确认前修改顺序

1. 扩写第 6.2 节，把决策归属和反陪跑规则挂到所有候选方案问题，不只挂到“提出方案”。
2. 修正第 2.2 节证据表述。
3. 写明 `quick_validate.py` 的实际调用方式，或替换为本仓库可执行检查。
4. 把安装副本同步移出仓库级 DoD；为 6 个行为场景补判定表和证据路径。
5. 再进入 `SKILL.md` 实施。
