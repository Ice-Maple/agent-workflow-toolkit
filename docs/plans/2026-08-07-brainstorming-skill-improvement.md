- 本机安装副本：`C:\Users\shterm\.codex\skills\brainstorming\SKILL.md`（仅用于本机生效检查，不属于仓库级完成条件）

## 1. 结论

本次不取消方案比较，也不通过增加更多方案来解决问题。任何向用户展示候选项的问题，都必须先判断它是否应由用户决定；其中真正的替代方案再把“候选方案比较”和“选定方案详细设计”明确拆成两个阶段：

1. 选择前，只比较真正可行的方案，并保持相同抽象层级和相近信息密度。
2. 推荐意见独立放在比较之后，基于已经确认的目标和约束给出；条件不足时不强行推荐。
3. 用户选定方向后，才详细展开该方案。
4. 只把真正属于用户的重大取舍交给用户，不把可由 Agent 推导的实现细节持续包装成 A/B/C 问题。

这套改造保留当前 Skill 的轻量定位，不引入 Superpowers 的全局硬门禁、任务状态、自动提交或后续 Skill 链。

## 2. 证据与问题界定

### 2.1 当前 Skill 中的结构性诱因

当前 `SKILL.md` 同时要求：

- 优先使用 A/B/C 选择题；
- 每次给出 2–3 个方案；
- 对方案说明做法、优点、代价和推荐理由；
- 把推荐方案放在第一个。

这些规则没有规定备选方案的最低完整度，也没有区分“方案比较”和“详细设计”。Agent 因而容易先完成推荐方案的设计，再把另外两个方向压缩成陪跑项。

### 2.2 真实会话表现

参考会话 `references/sessions/019fcfb1-5dff-7e43-8b99-d2beefc8901a-questions-and-choices.md` 中：

- 除最终落盘确认外，共有 27 个带候选方案的问题；
- 27 个问题全部把 A 标记为推荐项；
- 27 个问题全部只详细展开 A；
- B、C 通常只有一句做法或风险说明；
- 用户多数接受 A 或在 A 上补充实质约束；Q13 明确拒绝 A 并选择 B+C，Q27 明确选择 B。

这不能证明 A 的内容一定错误，但说明用户没有获得对其他方向同等充分的判断材料。选择过程更接近“确认 Agent 已完成的设计”，而不是共同比较不同取舍。

### 2.3 Superpowers 参考版的取舍

Superpowers 版本有一个值得保留的结构：先比较 approaches，再呈现选定方向的 design。当前简化版把这两个阶段合并了。

以下内容不应带回：

- 所有创造性任务都必须进入 Brainstorming 的全局硬门禁；
- 强制创建任务、自动提交设计文档；
- 强制跳转到 `writing-plans` 等体系内 Skill；
- 无论任务大小都走完整流程；
- 推荐方案必须排在第一位。

## 3. 改造目标

### 3.1 目标

- 让每个展示给用户的候选方案都具有真实可选性。
- 让用户能看见每个方案“为什么值得选”和“需要承担什么”。
- 避免推荐项通过顺序、篇幅和措辞获得不必要的优势。
- 保留 Agent 的专业判断，但明确判断依据和适用条件。
- 减少无意义的微观 A/B/C 决策和确认疲劳。
- 保持 Skill 简洁，不把一次头脑风暴扩张成重型设计流程。

### 3.2 非目标

- 不追求每个方案字数完全相等。
- 不要求任何问题都必须产生三个方案。
- 不随机打乱方案顺序来制造表面上的推荐分布均衡。
- 不禁止 Agent 推荐方案。
- 不修改可视化伴侣、落盘目录或“不自动开始实现”的既有边界。
- 本方案不直接修改 Skill，也不在当前任务中调用 Brainstorming Skill 做自我测试。

## 4. 核心设计

### 4.1 先判断决策归属

每次准备提问前，先把未确定内容分为三类。该判断适用于澄清阶段、方案比较阶段以及后续设计中的所有候选项问题：

| 类型 | 处理方式 | 示例 |
|---|---|---|
| 可查证事实 | 先探索或查证，不让用户凭空选择 | 当前代码是否已有缓存、现有格式是否支持某字段 |
| Agent 可推导的实现细节 | 根据已确认目标形成设计，在设计概要中让用户复核 | 内部函数拆分、局部命名、明显遵循现有约定的目录位置 |
| 用户拥有的重大取舍 | 作为单独问题比较或澄清 | 范围、体验、兼容性、成本、风险接受度、不可逆选择 |

只有第三类默认需要用户做选择。第一类应先调查，第二类不应连续转嫁给用户；即使第三类采用简短的澄清选项，也不得只详细展开推荐项。

以下情况可以把技术选择升级为用户决策：

- 会明显改变用户可见行为；
- 会扩大范围、成本或交付时间；
- 会形成难以撤销的架构或数据兼容承诺；
- 多个方向的优劣取决于尚未确认的用户偏好；
- 现有证据不足以让 Agent 可靠推导。

### 4.2 只展示真正可行的方案

展示候选方案前，先应用可行性门槛：

- 每个方案都必须满足已经确认的硬约束。
- 每个方案都必须存在至少一种合理场景，使理性的用户可能选择它。
- 不把明显无法达到目标的方向包装成“备选方案”。
- 不为了凑满三个而制造弱方案；两个方案足够，一个方案也允许。
- 只有一个可行方案时，直接提出该方案，并把其他方向列为“已排除方向”及原因，而不是伪装成平等选项。
- 混合方案只有在组合后形成清晰、可实施的新取舍时才列出，不能自动把各方案优点拼接成没有成本的第四项。

### 4.3 按问题类型控制比较深度

候选项问题分为两档，避免把所有澄清题都扩张成完整方案评审，也避免以“只是澄清”为由恢复陪跑项。

#### 4.3.1 真实替代方案

选择前，各方案按同一组字段比较：

| 字段 | 要求 |
|---|---|
| 核心做法 | 说明方向如何工作，不展开完整设计 |
| 主要收益 | 至少给出一个真实优势，说明为什么有人会选择它 |
| 主要代价 | 说明最重要的成本、风险或限制 |
| 适用条件 | 说明什么前提或偏好下最合适 |

约束如下：

- 所有方案保持相同抽象层级。
- 不在某一个方案中提前加入完整字段表、目录树、状态机或逐步流程，而让其他方案只有一句话。
- 不要求机械地保持相同字数；以信息字段齐全、比较粒度一致为准。
- 默认使用短表格或每项 2–4 句，防止“平衡比较”演变成同时设计三套完整系统。
- 方案使用描述性名称；A/B/C 只作为回复快捷标识，不承担“首选、次选”的含义。
- 排序按简单到复杂、保守到变革或其他与问题相关的中立轴进行，不按推荐顺序排列。

#### 4.3.2 目标或偏好澄清

澄清范围、优先级或偏好时可以使用更短的选项，不强制展开上述四字段，但必须满足：

- 每个选项表达一个真实、不同的选择及其关键影响或适用条件。
- 各选项保持相近粒度，不只给某一项增加机制、示例或优点。
- 不把可查证事实伪装成用户偏好。
- 不在用户表达偏好前标记推荐项；如果已有约束足以判断，则说明依据并作为建议提出。
- 不用“是否确认 A”代替中立的偏好澄清。

### 4.4 推荐与比较分离

推荐意见放在完整比较之后，单独标记为“当前判断”，不能嵌入某个选项使其获得额外展开。

推荐分两种情况：

1. **约束驱动的推荐**
   - 已确认的目标、成功标准和硬约束明显支持某个方案时，可以推荐。
   - 必须指出依据哪些已确认标准，以及推荐成立的前提。
   - 使用条件式表达，避免把判断包装成唯一正确答案。

2. **偏好驱动的选择**
   - 如果优劣取决于速度、灵活性、维护成本、控制力等用户尚未表达的偏好，暂不推荐。
   - 只问一个最能区分方案的问题，得到偏好后再形成推荐。

不采用以下做法：

- 因为 A 排在第一位就默认推荐 A；
- 为每个问题都强行给出推荐；
- 只写推荐项的优点、只写其他选项的缺点；
- 用“是否确认采用 A？”把接受推荐变成默认动作。

### 4.5 用户选择后再详细设计

方案比较结束后，询问用户选择、组合或调整哪个方向。用户选定后：

- 只详细展开选定方案；
- 逐节确认复杂设计，简单设计一次呈现即可；
- 不再反复把同一方向的普通实现细节变成选择题；
- 如果详细设计暴露出会改变原取舍的新成本或限制，重新打开相关方案选择；
- 如果用户选择非推荐项，直接沿该方向设计，不重复劝服用户回到推荐项。

### 4.6 改写选择问题

推荐的问法：

> 以上方向中，你更倾向哪一种取舍？可以选择 A/B、组合其中部分，或指出希望调整的地方。

当推荐依赖用户偏好时：

> 这里真正影响选择的是交付速度和后续灵活性的优先级。你现在更看重哪一个？

避免：

> 是否确认采用 A？

只有用户已经明确表达倾向、当前问题确实是在确认理解时，才使用“是否确认”。

## 5. 目标流程

改造后的流程为：

1. **探索项目上下文**：读取相关文件、文档和现状。
2. **识别决策归属**：在每次提问前区分事实、Agent 可推导细节和用户重大取舍。
3. **澄清目标与边界**：一次只问一个高价值问题；使用候选项时保持简短、真实和对称。
4. **比较可行方向**：只在存在真实替代方案时进行四字段、低细节比较。
5. **形成推荐或询问偏好**：推荐与比较分开，说明条件和依据。
6. **用户选择方向**：允许选择、组合、修改或否定现有方向。
7. **展开选定设计**：按复杂度分节确认，不再设计未选方案。
8. **呈现需求概要**：统一检查背景、目标、需求、约束和开放问题。
9. **确认并落盘**：用户确认后保存文档，到此结束，不自动实现。

## 6. `SKILL.md` 具体修改范围

### 6.1 核心原则

替换“优先用选择题”，增加以下原则，并明确它们适用于澄清、方案比较和后续设计中的所有候选项问题：

- 只询问用户拥有的重大取舍；可查事实先探索，可推导细节由 Agent 负责。
- 候选方案必须真实可行，不为凑数制造陪跑项。
- 选择前等深度比较，选择后才详细展开。
- 推荐基于已确认标准，并与方案描述分开。

### 6.2 澄清与方案比较流程

同时改写现有“逐个澄清问题”和“提出 2–3 个方案”：

1. 每次提问前先判断它属于可查事实、Agent 可推导细节还是用户重大取舍。
2. 澄清类选项保持简短，但每项都说明真实含义或关键影响；禁止推荐项单边详设和“是否确认 A”。
3. 只有存在真实替代方案时，才比较 2–3 个方向；一个方向也允许。
4. 真实方案按做法、收益、代价和适用条件等深度比较。
5. 推荐或澄清偏好，用户选定后再展开设计。

原有“呈现需求概要、确认、落盘、收尾”顺延，行为边界保持不变。

### 6.3 方案比较发送前检查

在 Skill 中增加一个短检查表：

- 每个选项是否都可能被理性用户选择？
- 真实方案是否都有做法、收益、代价和适用条件；澄清选项是否都有真实含义或关键影响？
- 是否在同一抽象层级比较？
- 是否只对某个选项提前进行了详细设计？
- 推荐是否依据用户已经确认的标准？
- 这个问题是否真的需要用户决定？

任一答案不满足时，先重写问题，不直接发送。

### 6.4 常见误区

补充以下反例：

- 推荐项详细设计、备选项一句话陪跑；
- 用两个明显较差的选项衬托推荐项；
- 为凑三个方案而制造没有适用场景的方向；
- 每个实现细节都问 A/B/C；
- 比较前就询问“是否确认采用 A”；
- 用户选择非推荐项后继续劝回推荐项。

### 6.5 落盘模板

把当前笼统的“方案”小节调整为：

```markdown
## 方案与决策

### 决策标准
- ...

### 选定方向
<选定方案和成立条件>

### 选择理由
<为什么符合目标和约束>

### 主要备选
<真正考虑过的方向及未选原因；没有则省略>
```

只记录重要方案决策，不记录每个微观实现选择。

### 6.6 Skill 正文体量预算

- 当前 `SKILL.md` 约 121 行；改造后目标为 150–180 行，硬上限 200 行。
- 通过替换和合并旧规则完成改造，不把本方案第 4 章原样追加进 Skill。
- 发送前检查保留 5–7 条短句，常见误区保持一行一条。
- 超出预算时优先删除解释性示例和重复表述，不删除决策归属、两档比较、推荐分离和选定后详设四项核心约束。
- 本次不为这些核心行为另建 Skill 内参考文档，避免规则因延迟加载而失效。

## 9. 验证策略

### 9.1 静态验证

- `python tests/brainstorming/validate_skill.py` 退出码为 0。
- `SKILL.md` frontmatter 仅保留非空的 `name` 和 `description`。
- `SKILL.md` 目标为 150–180 行，且不超过 200 行。
- `git diff --check` 无错误。
- 不出现 Superpowers、`writing-plans` 或自动提交依赖。

### 9.2 行为测试定义与隔离

`tests/brainstorming/cases.md` 为评估者使用的测试定义，每个 case 必须包含：

- case ID；
- 原始用户提示和必要的后续回复；
- 期望可见行为；
- 明确禁止的行为；
- 逐项通过/失败判定。

被测 Agent 只能获得原始用户提示、待测 Skill 和最小任务工作区，不能读取本方案、Grok 评审、测试判定或既有运行证据。每次运行在仓库外新建临时工作区，只复制待测 `SKILL.md` 和直接引用文件；使用外部 Codex CLI 的 read-only 模式，忽略项目规则并禁用 hooks 和 MCP。保留当前认证所需的用户配置；单轮 case 使用 ephemeral 会话，B-05、B-06 只为必要后续回复暂时保留会话。共享仓库的 native subagent 运行只能作为预检，不能计入完成证据。

### 9.3 行为验证场景

行为测试至少覆盖：

1. **只有一个可行方向**：Agent 不制造三个假方案。
2. **存在两个真实技术方向**：两项都说明做法、收益、代价和适用条件。
3. **选择依赖用户偏好**：Agent 先问关键偏好，不强行推荐。
4. **约束明显支持一个方向**：推荐出现在完整比较后，并说明条件。
5. **复杂设计包含多个细节**：Agent 只对重大取舍提问，不连续产生微观 A/B/C。
6. **用户选择非推荐项**：Agent 接受选择并沿该方向继续设计。

其中第 2、3、5 类为本次失效模式的高风险场景，各执行两次独立运行；其余三类各执行一次，共 9 次。全部运行必须使用同一份最终 Skill 内容及同一文件哈希。Skill 修改后，旧哈希的运行记录不能用于完成判定。

### 9.4 证据协议

运行证据保存到：

```text
tests/brainstorming/evidence/<YYYY-MM-DD>/<case-id>-run-<n>.md
```

每份记录包含：

- case ID 和运行序号；
- Skill 文件 SHA-256；
- 宿主、模型、CLI 版本和日期；
- 临时工作区路径和启动参数；
- 提供给 Agent 的原始提示和用户后续回复；
- Agent 的完整可见消息；可以保存为相邻的 raw turn 文件并由运行记录引用；
- 对照 case 判定表的逐项结果；
- 总体 PASS/FAIL；
- 若失败，失败行为和后续修订引用。

不得把凭据、认证头或环境秘密写入证据。所有 9 次最终有效运行都必须落盘，不能只保存通过样例。

### 9.5 行为验收标准

- 真实替代方案中的每个候选项都包含核心做法、真实收益、主要代价和适用条件。
- 目标或偏好澄清题中的每个候选项都表达真实含义或关键影响，不出现单边详细展开。
- 不存在只有负面描述、没有合理适用场景的陪跑项。
- 推荐不嵌入第一个选项，也不依赖选项字母或排列位置。
- 详细字段、目录、状态流等设计只在用户选定方向后展开。
- 每条消息仍然只提出一个需要用户回答的问题。
- 没有真实替代方案时允许只提一个方向。
- 用户无需连续确认 Agent 可以自行推导的普通实现细节。
- 不出现用“是否确认采用 A”代替偏好澄清或方案选择的行为。

九次运行必须全部满足各自 case 的判定表。任何失败都需要先修订 Skill，再基于新的统一哈希完整重跑 9 次，不能混用旧哈希证据。

## 10. 风险与控制

| 风险 | 控制方式 |
|---|---|
| 为了平衡而同时写三套完整设计，重新变复杂 | 选择前限制为统一四字段和低细节比较 |
| Agent 因害怕偏置而不再提供专业判断 | 允许基于已确认标准给出条件式推荐 |
| 把明显不合格的方向包装成可行方案 | 增加“理性用户是否可能选择”的可行性门槛 |
| 仍然出现大量微观选择题 | 增加决策归属判断，只询问重大用户取舍 |
| 规则只针对一个历史会话过拟合 | 使用多种新任务做独立行为验证 |
| 澄清题被四字段规则拉长 | 区分真实方案比较和简短澄清两档深度 |
| 新规则使 Skill 正文膨胀 | 目标 150–180 行、硬上限 200 行，优先替换和裁剪重复说明 |
| 本机仍加载旧安装副本 | 作为发布步骤同步并比较哈希，不混入仓库级完成条件 |

## 11. 完成定义

本次改造只有同时满足以下条件才算完成：

- 仓库中的 Skill 已按本方案修改；
- 仓库内静态校验脚本和 `git diff --check` 全部通过；
- 最终 Skill 不超过 200 行；
- 六类行为场景的 9 次最终有效运行均使用同一 Skill 哈希、有完整可复查记录并通过各自判定表；
- 最终证据中不出现推荐项单边详设、陪跑项或用“是否确认 A”代替真实选择的行为；
- Skill 仍保持轻量，不依赖 Superpowers 体系。
