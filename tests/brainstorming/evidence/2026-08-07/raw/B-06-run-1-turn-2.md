第一部分建议把集中清单定义为“唯一注册源”，而不是插件配置仓库。

### 职责边界

集中清单负责：

- 声明工具认可哪些插件。
- 提供插件的稳定标识和加载位置。
- 控制插件是否启用。
- 声明插件与宿主接口的兼容关系。
- 标明维护责任方，便于审查和故障定位。

集中清单不负责：

- 保存密钥或环境参数。
- 保存插件的大量业务配置。
- 替代插件包自身的版本管理。
- 在运行时自动回写注册信息。
- 通过扫描目录隐式注册未列入清单的插件。

### 最小数据模型

建议采用便于人工审查的 `plugin-registry.yaml`，插件以稳定 ID 为键，按 ID 排序：

```yaml
schema_version: 1

plugins:
  audit-exporter:
    name: Audit Exporter
    entrypoint: internal_plugins.audit_exporter
    enabled: true
    api_version: 1
    owner: platform-tools
    description: Exports audit records
```

字段含义：

- `schema_version`：集中清单自身的结构版本。
- 插件 ID：不可随显示名称变化，用于配置、日志和依赖引用。
- `name`：面向用户或管理员的显示名称。
- `entrypoint`：宿主能够解析的加载入口。
- `enabled`：明确控制是否参与加载。
- `api_version`：插件所使用的宿主插件接口版本。
- `owner`：负责维护和审批该条目的团队。
- `description`：可选的简短用途说明。

关键约束：

- 插件只有进入该清单后才算正式注册。
- ID 必须唯一；更名应保留原 ID。
- 清单只保存注册所需的最少信息。
- 业务配置放在独立配置体系中，通过插件 ID 关联。
- 禁止在清单中保存凭据。
- 新增、禁用、迁移责任方和删除插件都必须形成显式清单变更。
