已确定的设计边界：

- 对接 3 个外部 CLI adapter。
- `任务意图`、`执行尝试`、`完成判断`分别记录。
- 支持超时、取消和 resume。
- v1 不使用数据库、daemon 或完整 mailbox。
- 当前重点是恢复语义，而不是具体文件格式等可推导细节。

第一个必须明确的重大取舍是：编排器重启后，如果发现某次 CLI 执行已开始，但没有留下可靠的退出结果，应如何处理？

| 方向 | 核心行为 | 主要收益 | 主要代价 | 适用条件 |
|---|---|---|---|---|
| 保守暂停 | 将该尝试标记为“结果未知”，resume 时暂停任务，要求用户选择重试、确认完成或放弃 | 不会擅自重复有副作用的操作 | 恢复需要人工介入 | CLI 操作可能不可幂等，正确性优先 |
| 自动重试 | 将中断尝试视为未完成，按重试策略重新执行 | 使用简单，适合无人值守恢复 | 可能产生重复创建、重复提交等副作用 | 所有任务都可安全重试，或 CLI 自带幂等机制 |
| 按能力恢复 | 默认标记“结果未知”；只有 adapter 或任务明确声明可安全重试时才自动执行 | 同时兼顾安全性和自动化 | adapter 契约与状态判断更复杂 | 三个 CLI 的幂等性差异明显，且愿意维护能力声明 |

这三种方向取决于你能接受多大程度的重复执行风险，暂时不宜替你决定。对于“结果未知”的执行尝试，你倾向哪一种恢复行为？也可以指定默认行为及例外。
