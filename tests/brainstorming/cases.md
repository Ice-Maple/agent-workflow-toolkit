# Brainstorming Skill 行为测试定义

- 版本：1
- 用途：验证候选题决策归属、方案平衡、推荐时机和选定后详设
- 运行数：9
- 证据目录：`tests/brainstorming/evidence/<YYYY-MM-DD>/`

## 隔离规则

- 每次运行使用新的 Agent 上下文。
- 被测 Agent 只获得当前 case 的“原始提示”、必要后续回复、待测 Brainstorming Skill 和与提示直接相关的最小上下文。
- 不向被测 Agent 提供本文件中的观察点、禁止行为和判定标准。
- 不允许被测 Agent读取改造方案、评审记录、历史问题会话或既有运行证据。
- 所有有效运行使用同一个 `skills/brainstorming/SKILL.md` SHA-256。
- B-02、B-03、B-05 各运行两次，其余 case 各运行一次，共 9 次。

每次运行在仓库外创建新的最小临时工作区，只复制待测 `SKILL.md` 和它直接引用的 `visual-companion.md`。使用外部 Codex CLI 的 read-only 模式运行，忽略项目规则、禁用 hooks 和 MCP；保留当前认证所需的用户配置。单轮 case 使用 ephemeral 会话；B-05、B-06 仅为必要的后续回复保留会话，完成后不再复用。提示只引用临时工作区内的 Skill。证据必须记录临时工作区、CLI 版本和启动参数。共享当前仓库的 native subagent 输出只能作为预检，不能计入完成判定。

## 通用证据字段

每份运行记录包含 case ID、运行序号、Skill SHA-256、宿主、模型、CLI 版本、日期、临时工作区、启动参数、原始提示、必要后续回复、逐项判定和总体 PASS/FAIL。Agent 完整可见消息可作为相邻的只读 raw turn 文件保存并由记录引用。失败记录也必须保留。

## B-01：只有一个可行方向

### 原始提示

> 我想给一个已有 CLI 增加可选的 `request_timeout` 配置。它已经只有一个受版本控制的 `settings.yaml`，所有配置必须继续放在这个文件中，不能增加依赖、配置文件或新的存储机制，现有 YAML 解析与校验入口也必须复用。为兼容旧配置，字段缺失时必须保持当前 30 秒超时行为；配置新值时只接受正整数秒数。目标、范围和约束都已确定，请帮我形成简洁设计；这是独立的假设场景，不需要查看当前工作区。

### 期望可见行为

- 识别到只有一个满足硬约束的主方向，直接形成设计或只追问真正缺失的信息。
- 如提及其他方向，将其明确列为因违反约束而排除的方向。

### 禁止行为

- 为凑数把新 JSON 文件、数据库或环境变量包装成平等候选方案。
- 要求用户在明显违反硬约束的选项之间选择。

### 通过条件

两项期望均满足，且没有禁止行为。

## B-02：两个真实技术方向

### 原始提示

> 我们已经确认要为本地单用户 CLI 保存最近 100 次运行记录。候选方向是追加写入 JSONL，或者每次运行保存一个独立 JSON 文件；两者都满足现有约束。请先比较这两个方向，帮助我选择；这是独立的假设场景，不需要查看当前工作区。

### 期望可见行为

- 两个方向都说明核心做法、真实收益、主要代价和适用条件。
- 两边保持同一抽象层级和相近信息密度。
- 推荐如存在，位于完整比较之后，并说明判断依据和成立条件。
- 只提出一个需要用户回答的问题。

### 禁止行为

- 先长篇设计某一方向，再用一句话描述另一方向。
- 只写推荐项的优点和另一项的缺点。
- 把推荐当成用户已经选择，在同一消息中继续展开目录、字段、流程或实现细节。
- 以“是否确认采用 A”结束，而没有提供开放选择或修改空间。

### 通过条件

四项期望均满足，且没有禁止行为。

## B-03：选择依赖用户偏好

### 原始提示

> 我想设计一个首次配置页面，可以采用分步向导，也可以采用单页高级表单。目前还没有确定更重视新手引导还是熟练用户的操作效率。我希望继续使用纯文字，不使用可视化伴侣。请继续帮我梳理；这是独立的假设场景，不需要查看当前工作区。

### 期望可见行为

- 识别到当前选择取决于尚未确认的用户偏好。
- 一次只询问一个最能区分方向的偏好问题。
- 若提供简短选项，每项都说明真实含义或关键影响，粒度相近。

### 禁止行为

- 在取得偏好前推荐并详细设计其中一项。
- 把用户引向“确认 A”的默认动作。
- 同时提出多个独立问题。

### 通过条件

三项期望均满足，且没有禁止行为。

## B-04：约束驱动的条件式推荐

### 原始提示

> 我们要为低频、单用户的命令行工具保存任务历史，可以使用 JSONL 或 SQLite。两者都允许，但已确认最重要的标准是能直接查看和 Git diff，数据量不会超过 500 条，复杂查询不重要。请比较后给出你的判断；这是独立的假设场景，不需要查看当前工作区。

### 期望可见行为

- 先对 JSONL 和 SQLite 做等深度、低细节比较。
- 在比较之后给出条件式推荐，并引用已确认的可读性、可 diff、低数据量和弱查询需求。
- 不把推荐描述成脱离条件的唯一正确答案。

### 禁止行为

- 把推荐放入第一个选项并给予额外细节。
- 只描述 SQLite 的缺点而不说明其合理适用条件。

### 通过条件

三项期望均满足，且没有禁止行为。

## B-05：复杂设计中的决策归属

### 原始提示

> 我想设计一个轻量任务编排器。已确认：支持三个外部 CLI adapter；任务意图、执行尝试和完成判断分开记录；需要超时、取消和 resume；第一版不用数据库、daemon 或完整 mailbox。请继续梳理核心设计，但不要假设我已经决定了会影响用户行为或恢复语义的重大取舍。这是独立的假设场景，不需要查看当前工作区。

### 后续回复

若 Agent 提出合理的单个重大取舍问题，按其选项选择一个可行方向并要求继续。最多进行三轮，观察是否把普通字段、文件命名或内部函数拆分持续变成 A/B/C。

### 期望可见行为

- 只询问会改变外部行为、范围、恢复语义或不可逆承诺的重大取舍。
- 可查事实或普通实现细节由 Agent 推导，并在设计中供用户复核。
- 每轮只提出一个问题；用户选择方向后继续展开，不重新设计未选方向。

### 禁止行为

- 连续要求用户决定普通字段名、文件名、内部函数或明显遵循现有约束的细节。
- 在同一消息中提出多个独立问题。
- 每轮都给一个单边详设的推荐 A 并要求确认。

### 通过条件

最多三轮内三项期望均满足，且没有禁止行为。

## B-06：用户选择非推荐项

### 原始提示

> 我们要为内部工具增加插件注册表，可以采用单个集中清单，也可以采用每个插件自带 manifest。请平衡比较；默认团队规模小，但未来可能由多个团队分别维护插件。这是独立的假设场景，不需要查看当前工作区。

### 后续回复

如果 Agent 给出推荐，明确选择另一个仍然可行的方向，并说“我接受它的主要代价，请沿这个方向继续设计”。如果 Agent 暂不推荐，则先回答其偏好问题，再选择与其后续推荐不同的可行方向。

### 期望可见行为

- 接受用户对非推荐方向的选择。
- 直接沿该方向继续澄清或设计，并保留已确认的代价。
- 只有新发现会改变原取舍的重要事实时才重新打开选择。

### 禁止行为

- 重复劝说用户返回原推荐项。
- 继续详细设计已放弃的方向。

### 通过条件

三项期望均满足，且没有禁止行为。
