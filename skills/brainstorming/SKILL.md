# 头脑风暴：从想法到需求文档

通过自然对话把模糊想法梳理成清晰需求并落盘。保持轻量，只负责探索、决策和记录，不自动进入实现。

## 核心原则

1. **一次只问一个问题**：把复杂话题拆成多轮；用户已经说明的内容不要重复确认。
2. **先探索再提问**：先检查相关文件、文档、代码和最近改动，能够查证的事实不要让用户猜。
3. **只询问用户拥有的取舍**：Agent 能根据已确认目标和项目惯例可靠推导的细节，由 Agent 形成设计并供用户复核。
4. **候选项必须真实可选**：不为凑数制造陪跑项，不用明显较差的选项衬托推荐项。
5. **先比较，后推荐，选定后详设**：选择前保持同一抽象层级；只详细展开用户选中的方向。
6. **克制设计**：遵循 YAGNI，聚焦达成目标所需的最小范围。

## 可视化伴侣（按需）

遇到看图比读文字更清楚的问题（原型、布局、架构图、视觉对比）时，可以提供浏览器可视化伴侣：

- 第一次出现真正适合可视化的问题时，单独发一条提议，不同时提出其他问题。用户同意才使用；拒绝后不再重复提议。
- 即使用户同意，也要逐题判断：视觉问题用浏览器，文字或概念问题保持文字交流。
- 使用前先读本目录的 `visual-companion.md`。将自包含 HTML 写入 `docs/brainstorms/.visual/`，再用默认浏览器打开。

## 流程

### 1. 探索项目上下文

快速检查当前项目的相关文件、已有设计和最近改动。总结已经确定的事实，只针对真正缺失的信息提问。

### 2. 逐个澄清目标与边界

依次明确：

- 目的与用户：为什么做、谁会使用、解决什么问题？
- 范围与边界：包含什么、不包含什么、这次做到哪一步？
- 成功标准：什么结果算成功？
- 约束：技术、时间、兼容性和其他不可违反的条件。

每次准备提问前，先判断未确定内容属于哪一类：

- **可查证事实**：先探索或查证，不让用户凭空选择。
- **Agent 可推导细节**：依据现状和已确认目标形成设计，稍后供用户复核。
- **用户重大取舍**：单独提问，例如范围、体验、成本、风险接受度或不可逆选择。

澄清目标或偏好时可以给简短选项，但每项都要表达真实、不同的含义或关键影响，并保持相近粒度。用户尚未表达偏好时，不要只详细解释某一项，不要用“是否确认采用 A？”代替中立澄清。

用户回答已经足够时停止追问，进入方案比较或设计概要。

### 3. 判断是否存在真实替代方案

只展示满足已确认硬约束、并且在某种合理条件下可能被选择的方向：

- 不要求固定三个方案；通常使用 2–3 个，一个也允许。
- 只有一个可行方向时，直接提出它；把其他方向列为已排除方向和原因，不伪装成平等选项。
- 混合方案只有在组合后形成清晰、可实施的新取舍时才单独列出。

### 4. 等深度比较真实方案

选择前，以相同字段和相近信息密度说明每个方案：

| 字段 | 内容 |
|---|---|
| 核心做法 | 方向如何工作，不展开完整实现 |
| 主要收益 | 为什么有人会合理地选择它 |
| 主要代价 | 最重要的成本、风险或限制 |
| 适用条件 | 什么前提或偏好下最合适 |

保持低细节比较：

- 使用简短表格或每项 2–4 句，不同时设计三套完整系统。
- 不只在某个方案中加入字段表、目录树、状态机、完整流程或大量示例。
- 不追求机械的相同字数，但必须保持同一抽象层级和字段完整度。
- 使用描述性名称；A/B/C 只作为回复快捷标识。
- 按简单到复杂、保守到变革或其他中立轴排序，不按推荐顺序排列。

### 5. 推荐或询问偏好

把推荐放在完整比较之后，与选项描述分开：

- 已确认目标和约束明显支持某个方案时，可以给出“当前判断”，说明判断标准和成立条件。
- 优劣取决于尚未确认的用户偏好时，暂不推荐；只问一个最能区分方案的问题。
- 不为每个问题强行推荐，不只写推荐项的优点和其他项的缺点。
- 不在选项名称、字母、表格行或单元格中标记推荐；完整列完所有选项后再单独写“当前判断”。
- “当前判断”只包含结论、依据和成立条件；不得夹带该方向的字段、命名、目录、流程或实现建议。

用开放问题询问用户倾向哪个方向，或希望怎样组合、修改、否定现有方案。不要用“是否选择/确认推荐项”把接受推荐写成默认动作。

推荐不等于用户选择。发送比较和推荐后必须停下等待回复；同一条消息中不得继续给出选定方案才需要的目录、字段、流程或实现细节。

### 6. 详细展开选定方向

用户选定后才详细设计：

- 只展开选定方向；不要继续设计未选方案。
- 简单设计一次呈现；复杂设计按小节呈现，每次确认一个连贯部分。
- 普通实现细节由 Agent 根据已确认方向补全，不连续制造微观 A/B/C。
- 新细节如果暴露出会改变原取舍的重要成本或限制，重新打开相关选择。
- 用户选择非推荐项后，沿该方向继续，不重复劝回推荐项。

### 7. 呈现需求概要

根据复杂度组织简洁小节，覆盖：

- 背景与目标
- 核心需求（功能与非功能）
- 重要方案决策及理由
- 约束
- 待定问题
- 下一步

请用户确认概要。存在异议时回到相关问题，不要跳过确认直接落盘。

### 8. 落盘并收尾

确认后，将文档保存到 `docs/brainstorms/YYYY-MM-DD-<topic>.md`：

- 文件夹不存在就创建。
- 日期使用当天；`<topic>` 使用简短的 kebab-case 英文或拼音标识。
- 默认只写文件，不提交 Git，除非用户明确要求。

告诉用户保存路径和仍待决定的问题。到此结束，不自动开始实现或调用后续 Skill。

## 候选题发送前检查

- 这个问题是否真的需要用户决定？
- 每个选项是否都可能被理性用户选择？
- 澄清选项是否都有真实含义或关键影响？
- 真实方案是否都有做法、收益、代价和适用条件？
- 是否只对某个选项提前进行了详细设计？
- 推荐是否依据用户已经确认的标准、放在比较之后，且没有提前出现在选项名称或表格中？
- 用户是否已经明确选定方向；如果没有，是否在比较后停下而未继续详设？

任一项不满足时，先重写问题。

## 文档模板

```markdown
# <主题标题>

- 日期：YYYY-MM-DD
- 状态：草案 / 已确认

## 背景与目标
<为什么要做，想达到什么效果>

## 核心需求
<功能与非功能需求>

## 约束
- ...

## 方案与决策
### 决策标准
- ...
### 选定方向
<选定方案和成立条件>
### 选择理由
<为什么符合目标和约束>
### 主要备选
<真正考虑过的方向及未选原因；没有则省略>

## 开放问题
- [ ] ...

## 下一步
- ...
```

## 常见误区

- 推荐项详细设计，备选项只有一句话。
- 用两个明显较差的选项衬托推荐项，或为凑三个方案制造无效方向。
- 每个实现细节都问 A/B/C，让用户替 Agent 完成设计。
- 比较前就询问“是否确认采用 A”。
- 用户选择非推荐项后继续劝回推荐项。
- 没探索就提问、过度设计、没确认就落盘或自动开始写代码。
